# 穩健性稽核：換一份書表會在哪裡炸開

> 回答的問題：**如果地政局給我們一份不同標的、不同結構、不同數值的查估書表，
> 系統撐不撐得住？**
>
> 所有結論都來自實際執行 `stress/audit.py`（61 個案例，值的變異）與
> `stress/variants.py`（16 個案例，結構的變異）。
> 重跑方式見 `stress/README.md`。

---

## 一句話結論

**計算層很穩，辨識層很脆，中間的驗證防線裝好了但沒接上。**

風險不是平均分佈的。`kernel/` 是真正資料驅動、失敗時會明確說原因；
`parser/` 幾乎每個座標常數都是對著官方範本這一份 PDF 量出來的。
換數值、換標的數、換規則集都撐得住；**換版面會直接倒**。

---

## 為什麼用合成測資，而不是找真實資料

先說清楚方法上的限制。

我試過三次網路搜尋（土地徵收補償市價查估、地價區段勘查表、新北市地政局評價基準），
搜尋工具回傳的全部是日本國土交通省的用地補償資料，抓不到任何台灣的公開書表。
**這條路走不通，所以改用合成測資。**

換個角度想，這反而更適合定位問題：合成測資可以**一次只改一個變數**，
炸開時能精準指出是哪個假設失效。隨機找到的真實檔案如果讀不出來，
反而分不清是哪一層的問題。

代價是：**沒有測到真正不同版面的 PDF。** 這是本次稽核最大的盲區，見第 8 節。

## 2. 分層評估

### ✅ `kernel/` — 穩。真正的資料驅動

| 測試 | 結果 |
| --- | --- |
| 刪掉一個 factor（28 → 27） | 查 76 格，該項列入查不動 |
| 只留 3 個 factor | 查 52 格，25 項列入查不動 |
| `factors` 空陣列 | 不崩，區域層全部列入查不動 |
| `factor_id` 改名 | 該項變成查不動，其餘照跑 |
| `classifier.type` 改成不支援的值 | 該項變成查不動，其餘照跑 |
| 混用 2 級／3 級／5 級 | 已經在用了：regional 有 3 個二級項、individual 有 3 個二級與 1 個三級 |

**判級失敗時會 raise `ValueError` 並說明原因**，而 `review()` 接住它放進
`not_checkable`。這個「優雅降級而且誠實回報」的設計是整個系統最可靠的部分。

**規則即資料的主張站得住。** 我造了兩份合成的假行政區規則集
（級距 ×1.5／step ×2、以及級距 ×0.8／step ×0.5，`max_range` 同步縮放），
兩份自檢都是 ERROR=0，套到同一份未修改的官方範本分別得到 **5 處與 4 處不符**。
程式一行都沒改。

### ✅ 缺表處理 — 穩

7 種組合全部優雅降級，而且 `checked` 格數誠實反映實際查了多少：

| 有哪些表 | 查了幾格 |
| --- | --- |
| 只有表1 | 28 |
| 只有表5-2 | **0**（沒有可查的東西，誠實回報） |
| 只有表4 | 20 |
| 表1+表5-2 | 56 |
| 表1+表4 | 48 |
| 表5-2+表4 | 21 |
| 三張都有 | 77 |

### ✅ 比較標的數量 — 穩，但權重容忍度為零

1～3 件都正確加權：

| 件數 | 權重 | 比準地比較價格 |
| --- | --- | --- |
| 1 | 100 | 212,958 |
| 2 | 70／30 | 216,416 |
| 3 | 50／30／20 | 221,026 |

4 件會 raise，訊息有法源依據（辦法第 19 條規定 1～3 件）。這是正確行為。

### ✅ 產表 round-trip — 穩

`parse → fill → render → 再 parse`：價格一致、19 個 facts 全數還原。
自己產出的 PDF 讀得回來，這是不錯的穩健性訊號。

### 🚨 `parser/` — 脆。全部座標常數都是對這一份範本量出來的

這一層**沒有被本次測試覆蓋**（我沒有不同版面的 PDF），
但從程式碼可以直接判斷風險。見第 4 節。

## 3. 風險清單

按嚴重度排序。每一項都標註**失效時的表現**，因為「靜默給錯答案」比「爆掉」危險。

### 🔴 R1 — 權重加總不是 100 就硬失敗

| | |
| --- | --- |
| 表現 | `ValueError: 權重合計必須為 100%，實得 99%` |
| 觸發 | 3 件標的各填 33%（合計 99），或 70/29、70/31 |
| 為什麼危險 | **33+33+33=99 是很自然的填法。** 真實表單四捨五入後很容易不是整 100 |
| 位置 | `kernel/src/compute.py` `benchmark_comparison_price()` |
| 修正難度 | **低**。允許 ±1% 的容差，或按比例正規化後再算，並發 WARN 而不是 raise |
| 要不要修 | **要**。丟一份新資料進來最可能先炸這一個 |

### 🔴 R2 — `dec()` 對非數字丟 `InvalidOperation`，不是 `ValueError`

| | |
| --- | --- |
| 表現 | `decimal.InvalidOperation` → API 層接不住 → **HTTP 500** |
| 觸發 | 單價為 `None`、`""`、`"無"`、或**帶千分位的 `"184,763"`** |
| 為什麼危險 | `/api/compute` 與 `/api/review` 接受用戶端傳來的任意 `tables` JSON，不是只有 parser 的輸出。500 而不是 422，前端也顯示不出有用訊息 |
| 位置 | `kernel/src/ruleset.py` `dec()` |
| 修正難度 | **很低**。`classify.py` 已經做過一次同樣的轉換（把 `ArithmeticError` 轉成 `ValueError` 並說明收到什麼），照抄那個做法即可 |
| 註 | 正常流程不會踩到：`parser` 的 `_to_number()` 會 `replace(",", "")`。所以這是 API 邊界的問題，不是內部邏輯的問題 |

### 🔴 R3 — 完全沒有合理性檢查，荒謬價格會靜默通過

| | |
| --- | --- |
| 表現 | **不報錯、不警告，`verdict=match`** |
| 實測 | 單價 −184,763 → 比準地地價 **−212,958**，審查結論「相符」<br>單價 0 → 地價 0，審查結論「相符」<br>單價 1e12 → 地價 1,152,600,000,000，審查結論「相符」 |
| 為什麼危險 | 這是**最危險的一類**：系統不是壞掉，是自信地給出錯的答案。如果 parser 誤讀一個數字（少一位、多一位、吃到負號），整份審查會回報「相符」 |
| 位置 | 沒有任何地方做這件事 |
| 修正難度 | **低**。在 `review()` 加一組合理性檢查，把違反的項目放進既有的 findings 或新增 `sanity` 區塊：單價須 > 0、修正率絕對值須 ≤ 100、地價不得為負 |
| 要不要修 | **要**。這是唯一會安靜給出錯答案的類別，其餘都會明確報錯 |

### 🟠 R4 — 規則集自檢很完整，但執行期從來沒被呼叫

`kernel/src/validate.py` 的 `check_ruleset()` 有 12 種檢查
（BAND_GAP、BAND_OVERLAP、BAND_INVERTED、GRADE_SET、MATRIX_SHAPE、
MATRIX_DIAGONAL、MATRIX_ASYMMETRY、MAX_RANGE_MISMATCH、UNIT_UNKNOWN、
MOI_CAP_* 等），寫得很好，而且**實測抓得到問題**：

| 我製造的問題 | `check_ruleset` 的反應 | `review()` 的反應 |
| --- | --- | --- |
| 級距挖洞（建蔽率移除第 3 級） | **2 個 ERROR**（GRADE_SET、BAND_GAP） | 查 77 格、0 處不符、0 查不動 —— **完全沒發現** |
| 級距重疊 | **3 個 ERROR** | 同樣沒發現 |
| step ×2 而 `max_range` 沒同步 | **28 個 ERROR**（MAX_RANGE_MISMATCH） | 照算 |

`review()` 沒發現是因為官方範本的建蔽率是 70%，落在第 1 級，
**沒踩到那個洞**。規則集有缺口時不會主動被發現，只有踩到才會。

| | |
| --- | --- |
| 表現 | 壞掉的規則集靜默載入並產出結果 |
| 位置 | `api/main.py` 的 `_load()` 沒呼叫 `check_ruleset()`。它只在 `kernel/demo.py` 與測試裡被用 |
| 修正難度 | **很低**。`api/kernel_api.py` 已經把 `check_ruleset` 與 `errors` 匯出了，`_load()` 加三行：有 ERROR 就 raise `HTTPException(500, ...)`，或至少把 findings 放進回應 |
| 附帶發現 | `MATRIX_ASYMMETRY` 與 `MATRIX_DIAGONAL` 兩條檢查目前是備而不用 —— 全部 47 個 factor 都是 `linear_step`，而 `(j-i)*step` 數學上必然反對稱且對角為 0。要等有 `cells` 型的規則集才會發揮作用 |

### 🟠 R5 — 表格跨頁時，審查與產表的行為不一致

| | |
| --- | --- |
| 表現 | 審查正常跑完，但**只產出兩張書表而不是三張**，且沒有任何訊息說明少了哪一張 |
| 實測 | 表4 出現兩次時：辨識路徑得到 `['表1','表4','表5-2']`（取第一頁繼續跑），產表路徑得到 `{'表1': 1, '表5-2': 2, '表4': '跳過'}` |
| 原因 | `api/main.py` 的 `parse_forms` 用 `if code in tables: continue` 取第一個；`pdfform/forms.py` 的 `_find()` 用 `find_page()`，遇到重複會 raise `LookupError`，然後被 `except LookupError: return None` 吞掉，整張表跳過 |
| 為什麼會遇到 | 真實案件的表格很可能跨頁。範本只有 1 件比較標的，表4 塞得下一頁；3 件的案子未必 |
| 修正難度 | **低到中**。短期：讓兩邊行為一致（都取第一頁，或都明確報錯）。長期：支援跨頁合併，那是中等工作量 |

### 🟡 R6 — 無效等級只被當成「填錯」，不是「這不是合法等級」

| | |
| --- | --- |
| 表現 | 表1 等級填 `9`、`0`、`-1`、`"3"`、`None` 都只回報「與重算結果不符」 |
| 為什麼有影響 | 審查員看到的訊息會誤導。「你填 9 但應該是 3」和「9 根本不是 1..5 的合法等級」是兩種不同的問題，前者是判斷錯誤、後者是資料損毀或辨識錯誤 |
| 修正難度 | **低**。在第一層檢核前加一個等級合法性檢查 |
| 要不要修 | 可以不修，但要知道 |

### 🟡 R7 — 規則集缺必要欄位時是 `KeyError`

刪掉 `grade_labels` / `scope` / `ruleset_id` / `max_range` / `matrix` / `classifier`
都得到裸 `KeyError`，訊息只有欄位名，沒說是哪個檔案、哪個 factor。

| | |
| --- | --- |
| 修正難度 | **低**。`load_ruleset()` 加一層 schema 檢查，錯誤訊息帶上檔名與 factor_id |
| 要不要修 | 不用。只有自己編規則集時會遇到，錯誤訊息雖然簡陋但夠找 |

### 4.1 🚨 版面相關 —— 換版面就失效（最高風險）

這些數字全部是對著**官方範本這一份 PDF** 量出來的。註解甚至寫明了量測過程，
誠實但也暴露了脆弱性。

| `table4.py:379` | `w.top < 55` | 找「實例編號」 | 同上 |

**失敗是大聲還是安靜，要分開看。** 原本推測這些失效多半是靜默的，實測後修正：

- **欄索引類（`PANELS`、`COL_*`）是大聲失敗。** 位移後讀到 0 項或直接拋
  `LookupError`，不會產出錯誤答案。定位方式見第 9 節。
- **座標容差類（`y_tol`、`INSIDE_TOL`）仍未實測，推測可能是靜默的。**
  容差算錯不拋例外，只會取到隔壁格的值，然後照樣算出一個「看起來合理」的答案。
  要驗證需要一份真的改過版面的 PDF，見第 8 節盲區。

## 5. 應該保留哪些彈性

拿到一份新的書表時，最可能卡住的順序是這樣。第 10 節有症狀對照的速查表，
這一節說明的是「為了少卡一次，事前可以留哪些彈性」。

### 第一關：`detect_table` 認不認得出表別

如果標題用字不同或前面多了字，整頁會被當成非書表，後面全部不會發生。

**建議準備的彈性**：把 `_NAMES` 的比對從「完全包含」放寬成「關鍵字子集」，
並把 `page.words[:12]` 放寬到 `[:30]`。或者加一個手動指定表別的參數。
`parser.cli` 已經支援指定表別，可以繞過偵測驗證後面的流程還通不通。

### 第二關：欄位對照表對不上

`table4.py` 的 `FACTOR_ROWS` 帶列號（`"7面積(M2)"`），列號一改就對不上。

**建議準備的彈性**：改成只比對去掉開頭數字後的名稱。這是幾行的改動，
而且註解已經寫了「這張對照表是資料不是邏輯，換書表版本只改這裡」——
作者本來就預期這裡要改。

### 第三關：座標常數

`EDGE_MIN_SPAN`、`y_tol`、`w.top < 65` 這些。

**建議準備的彈性**：把它們提成模組層級的可覆寫參數（環境變數或函式參數），
這樣不改程式碼就能調。目前 `column_edges()` 已經接受 `min_span` 參數，
但 `parse()` 沒有把它透出來。

### 止損策略

如果一份新書表怎麼調都讀不出來，**不要在 parser 上耗超過 30 分鐘**。
改用這條路：手工把那份書表的值填成 `tables` JSON，直接打 `/api/compute`
與 `/api/review`。計算層是穩的，這樣至少能證明審查邏輯對新案件有效，
而辨識失敗可以誠實說明是版面差異。

## 8. 這次沒測到的（盲區）

誠實列出來，這些是還不知道答案的問題。

1. **真正不同版面的 PDF。** 這是最大的盲區。所有 parser 的風險評估來自讀程式碼，
   不是實測。找不到台灣的公開書表（見開頭），也沒有第二份官方範本。
2. **掃描件。** 只讀文字層，沒有測過影像 PDF。可以確定讀不出來，但沒測過失敗的表現
   是拋例外還是回空。
3. **跨區段案件。** 需要兩張表1，範本只有一張。比較標的的區域因素等級目前沿用比準地。
4. **表5-2 的區域修正矩陣。** `review()` 從來不用它（只用 classifier 做第一層），
   所以壓力測試中把 regional 的 matrix 改壞完全沒有影響。這也印證了
   「表5-2 引擎尚未回灌表4」這個已知限制。
5. **前端。** 本次只測後端。後端回應多一個鍵或某個欄位變 `null` 時，
   前端會不會壞掉沒有測。
6. **併發與大檔。** 沒測多人同時上傳、沒測 50 頁的 PDF。

### 想補第 1 項的話

最實際的做法是用 `pdfform` 產出一份書表，然後**手動在 PDF 編輯器裡調整版面**
（改行距、加一欄、移動表頭），再丟回系統。這樣才能真的測到座標常數的容忍範圍。
估計 1 小時，但只有在確定要投資 parser 穩健性時才值得做。

## 9. 結構變異的實測行為

第 4 節列的是「哪些東西寫死了」，這一節是「寫死的東西被打破時實際會發生什麼」。
來源是 `stress/variants.py`，16 個案例，**沒有一個是靜默失敗**。

書表的結構變異其實是三種不同的事，容忍度差很多：

| 變異 | 實測行為 | 需要改的東西 |
| --- | --- | --- |
| 檔案怎麼切 | ✅ 本來就支援 | 不用改 |
| 列的順序、增減、名稱 | ✅ 用文字找列，順序無關 | 對照表（純資料） |
| 欄的位置 | ⚠️ 表1／表5-2 會失敗，但大聲 | 3–6 個常數 |
| 用地類別 | ⚠️ 需要對應規則集 | 一份 JSON |

### 9.1 檔案怎麼切 —— 不受影響

`detect_table()` 依頁首標題判斷而非頁碼，且要求表別代號與正式名稱同時出現才算命中
（所以範本裡 3 頁區段圖不會被誤判）。實測：

| 案例 | 結果 |
| --- | --- |
| 只含表1／表5-2／表4 的單頁檔，各自上傳 | 三份都正確辨識 |
| 三份結果合併後送審查 | 查核 77 格、不符 2 處，與一次送三表相同 |
| 只送表4 | 查核 20 格，第一二層跳過，不崩 |
| 只送表1 | 查核 28 格，第二三層跳過，不崩 |
| 只送表5-2 | 查核 0 格，三層全跳過（見下方說明） |
| 完全無關的 PDF | HTTP 400，訊息明確 |

**只送表5-2 會查核 0 格**，這不是缺陷而是設計結果：第一層在表1 內部比對、
第二層要表1 與表5-2 對照、第三層要表5-2 與表4 對照，所以表5-2 單獨存在時
沒有任何一層湊得齊。畫面上會顯示 0 格，符合「`checked` 格數必須誠實回報」的原則。

`/api/parse` 一次收一個檔，多檔情境靠前端連續上傳後合併 `tables` 再送審查。

### 9.2 列的變異 —— 不受影響

定位是掃過所有列做名稱前綴比對，不是用列號索引：

```python
def _find_label_row(rows, alias, panel):
    for idx, row in enumerate(rows):          # 掃全部列
        for col in PANELS[panel]["labels"]:
            if _flat(row[col]).startswith(alias):
                return idx
```

所以列的順序調換、中間插入新列、刪掉某幾列、值黏在標籤後面
（`區段內道路平均寬度 12 M`）都不影響。找不到時記 `factor_row_not_found`
警告並跳過該項，其他項照常。

實測在對照表加入兩個書表上不存在的細項：讀到 28 項、2 則找不到警告，其餘不受影響。

### 9.3 欄的變異 —— 會失敗，但看得見

表4 的欄界是從框線動態算出來的，只有一個門檻常數。實測容忍範圍：

| `min_span` | 抓到欄界 | 結果 |
| --- | --- | --- |
| 100 | 15 條 | 可用 |
| 200（預設） | 11 條 | 可用 |
| 300 | 6 條 | 可用 |
| 400 | 3 條 | `parse()` 拋 `ValueError`「表4 框線不足」 |
| 600 | 0 條 | 同上 |

表1 與表5-2 是寫死欄索引的。把索引整體右移一格（模擬多一欄）實測：

| 表 | 行為 |
| --- | --- |
| 表1 | 讀到 0 項，28 則 `factor_row_not_found` 警告 |
| 表5-2 | 拋 `LookupError`「表5-2 找不到 '主要項目' 這一列」 |

**兩者都是大聲失敗**，不會產出「看起來正常但數字錯」的審查報告。
這修正了第 4.1 節原本的推測。
